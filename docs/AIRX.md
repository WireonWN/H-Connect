# Ядро AirX

AirX выполняет сетевые операции Horizon Connect
Клиент передаёт конфигурацию и команды управления, ядро устанавливает соединение с сервером, обрабатывает трафик и сообщает о состоянии сессии

Основная логика ядра написана на Rust
На Android связь с приложением проходит через Kotlin/JNI, настольные клиенты используют отдельный процесс ядра

## Разделение задач

| Уровень | Ответственность |
| :--- | :--- |
| Клиент | Интерфейс, список серверов, подписки и пользовательские настройки |
| Платформенная интеграция | Создание сетевого интерфейса, разрешения ОС, маршруты и события сети |
| Управление сессией | Состояние подключения, действующая попытка соединения, остановка и восстановление |
| Протокольный модуль | Согласование с сервером, формат сообщений и обработка данных протокола |
| Передача трафика | TCP-потоки, UDP-обмен, IP-пакеты и очереди |
| Общие службы | DNS, правила маршрутизации, ограничения ресурсов и диагностика |

Логика протокола и работа с реальными сокетами разделены
Обработка сообщений и переходы состояний отделены от сетевого ввода-вывода

## Путь трафика

Упрощённая схема системного VPN-подключения:

```mermaid
flowchart LR
    A[Приложения] --> B[TUN]
    B --> C[AirX]
    C --> D[Выбранный протокол]
    D --> E[Сервер]
    E --> D
    D --> C
    C --> B
    B --> A
```

**Потоковые прокси-протоколы**

Для VLESS, VMess, Trojan и других прокси-протоколов ядро преобразует трафик из TUN в соединения или обмен датаграммами
TCP-движок обрабатывает состояние соединения, подтверждения и буферы
Для UDP ведутся отдельные соответствия между локальным потоком, удалённым адресом и протокольным каналом

**Пакетные туннели**

WireGuard, AmneziaWG, OpenVPN и IKEv2/IPsec работают с IP-пакетами
Их путь передачи сохраняет правила конкретного туннеля, включая ограничения адресов и параметры, согласованные с сервером

**Локальный прокси**

В режиме локального SOCKS5 приложение направляет соединения на прокси-порт клиента
Такой путь может работать без системного перехвата всего трафика через TUN
Доступные режимы зависят от платформы и сборки

## Состояние подключения

В ядре есть общий механизм управления жизненным циклом сессии
Он принимает результаты от платформенного слоя и протокольных исполнителей

Основные этапы:

1. Проверка конфигурации и подготовка сетевых параметров
2. Создание попытки подключения
3. Согласование соединения с сервером
4. Подтверждение готовности выбранного пути
5. Передача пользовательского трафика
6. Завершение операций и освобождение ресурсов

Готовность сокета, успешное согласование протокола и прохождение трафика учитываются отдельно
Ответ на обычный пинг сервера сам по себе не подтверждает работоспособность VPN

Каждая сессия имеет идентификатор и поколение
При остановке или смене подключения операции проверяют, что относятся к действующему состоянию
Это используется для отклонения запоздавших ответов, отмены фоновой работы и закрытия старых сетевых ресурсов

## Память и очереди

Учёт ресурсов охватывает объём буферов, количество элементов очередей и число одновременно выполняемых операций
Ресурсы резервируются в рамках заданного лимита и освобождаются после завершения работы

Ограниченные очереди позволяют обработать перегрузку явно
Поведение при заполнении зависит от пути передачи: операция может ожидать освобождения места, завершиться ошибкой или отбросить UDP-датаграмму

Размеры лимитов зависят от конфигурации и сборки
Фиксированное потребление памяти для всех протоколов и нагрузок не заявляется

## DNS и маршрутизация

Разрешение имён, выбор DNS-сервера и применение доменных правил выделены в отдельные компоненты
Доступны реализации обычного и зашифрованного DNS, но их подключение различается между режимами

Маршрутизация потоковых протоколов и пакетных туннелей использует разные пути обработки
Наличие пункта настройки не означает одинаковую совместимость со всеми протоколами

Расширение доменной маршрутизации для WireGuard, AmneziaWG, OpenVPN и IKEv2 находится в интеграции
Доступность определяется конкретной сборкой клиента

## Реализации и зависимости

В проекте разрабатываются протокольные адаптеры, управление сессиями, правила передачи данных и учёт ресурсов
При этом ядро использует сторонние компоненты

| Компонент | Примеры используемых решений |
| :--- | :--- |
| Асинхронный ввод-вывод и таймеры | Tokio |
| TLS и криптография | rustls, ring, BoringSSL в соответствующих путях |
| TCP и QUIC | Собственные реализации и сторонние реализации в зависимости от сборки и режима |
| Системная сеть | Сокеты, TUN-интерфейсы и механизмы маршрутизации ОС |

Точный состав зависимостей определяется платформой и включёнными модулями
Часть зависимостей содержит C, C++ и ассемблерный код

## Интеграция с платформами

| Платформа | Связь клиента с ядром | Системная интеграция |
| :--- | :--- | :--- |
| Android | Kotlin/JNI | Android VPN-интерфейс, защита исходящих сокетов от попадания обратно в VPN |
| Windows | Отдельный процесс ядра | TUN-интерфейс, маршруты, DNS и очистка сетевых настроек |
| Linux | Отдельный процесс ядра | Локальный прокси либо Linux TUN в сборках с соответствующей интеграцией |

У платформ разные сетевые API и порядок настройки интерфейса
Поэтому одинаковое название протокола не означает полного совпадения настроек и режимов между Android, Windows и Linux

## Версии

Версия AirX ведётся отдельно от версии Horizon Connect
Обновление интерфейса может не менять ядро, а исправление сетевой части может выходить без переработки интерфейса

Список включённых функций и известных ограничений указывается в описании релиза
